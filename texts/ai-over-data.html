An LLM assistant over a data warehouse: design notes

How an assistant that answers business questions from an employer's warehouse was rebuilt around the data catalogue, a cross-checking protocol and least-privilege tools, told from the author's records without internal figures.

Overwhelmed? Here's the short version
  • The assistant reads business definitions from the catalogue and, when a certified dashboard carries the same measure, reports how far its figure differs; otherwise it labels the answer unreconciled. How often such a dashboard exists is not published.
  • Its scores are not published, so this page describes a design, not how well it performs.
  • Write access was removed and every run has hard caps and a pseudonymous trace.
  • The work system rests on the author's records (private; not verifiable); the employer and its internal figures are not named.

What the assistant does and how it is built

Non-technical staff want answers to questions such as how many active customers did we have in Q2 in one market. The assistant lets them ask in their own words and returns a number, a chart and the query that produced it. It is judged on a fixed set of real questions with verified answers, as the shares that come back correct, come back wrong without saying so (a silent failure), or are correctly declined; such sets are called golden sets, and those shares are kept at work and not reported here1.

The version I inherited was a bespoke NL→SQL (natural language to SQL) service: retrieval of similar past queries, a custom pipeline of prompts, and code that encoded what the business meant by its own words. It was replaced by a much smaller agent built as a graph of steps on a commercial model API, with MCP (Model Context Protocol) connectors, adapters that expose each system to the model as callable tools, to the warehouse, the data catalogue with its glossary, and the certified dashboards. It had to match the old service on the golden sets before replacing it; the share of matching answers and the tolerance are part of the private record1.

The main design choice keeps domain knowledge in the data catalogue, as the glossary terms, descriptions and lineage that analysts already maintain, and has the agent read it at run time, so the codebase holds nothing about what a "customer" or a "tier" means. The agent looks the question's terms up in the catalogue, finds the certified figure if one exists or writes a query, runs it read-only, reconciles the result and answers with its provenance. Each step is a separate node of the graph with declared inputs and outputs, so the sequence of steps and tools in a run can be reconstructed from its trace, though not replayed exactly, since the trace keeps no raw tool output. Lookup tools replace a schema dump in the prompt, so a definition fixed in the catalogue reaches the agent on its next run without a code or prompt change. Text-to-SQL benchmarks such as Spider and BIRD score the SQL a model writes23, and semantic layers such as the dbt Semantic Layer and LookML keep metric definitions in one governed place45. This design is closest to the second, with the existing catalogue in the role of the semantic layer.

The trust protocol and the golden sets

Before a figure reaches the user, business terms resolve through the glossary before any SQL is written; the intention is that "active customer" means what the company decided it means, which is a design aim, not a measured property. When a certified dashboard carries the same measure, the assistant's figure is compared with it and the difference is reported; when none exists, the answer says it is unreconciled. The harness scores whether each run followed the protocol as well as whether it was correct. What counts as agreement with a dashboard, and how often a certified figure exists at all, are not published here1.

The golden sets came from the first business proof of concept, which ran with business users in the room; their real questions became date-fixed golden cases with verified answers. Each definition they argued about was settled and written into the catalogue's glossary, where the agent reads it. The golden sets run on every change, with the intention that a change that improves one score at the cost of another is visible before it ships; how often that has happened is not reported here1.

Quaesitor, an exploratory harness I ran on commercial models rather than on the work system (not pre-registered; harness and run reports private), plants the usual causes of a wrong number in synthetic and real warehouses and asks questions with known answers three times each6. Of its 5 794 answers, 66 % were silently wrong; among the 3 704 numeric answers from five packs the share ranged from 56 % to 88 % across packs and from 76 % to 92 % across model configurations7, and on three smaller warehouses (10 to 80 cells per model) from 20 % to 80 % of all cells per model, declined cells included6. The traps are planted, so these rates say nothing about production. Whether a run-time signal can tell wrong answers from right ones is the subject of a separate study, Can a wrong number be seen coming?, which reports its own estimates and their uncertainty7.

Tool surface, privileges, cost caps and tracing

The tool surface and the privileges changed after a design discussion (private; not verifiable). The connectors exposed many more tools than an assistant that answers questions needs, some of them able to write, so only a read-only allowlist (a fixed list) remains, and a scoping wrapper rejects any query that reaches outside the user's project. The assistant also ran as a service account, a confused deputy through which a user could do what the user's own credentials could not, so access is now enforced by the warehouse's own access permissions, per data domain, rather than by a prompt instruction1.

The cost caps came from a recorded incident: a single unbounded question ran up a large token bill without failing, because nothing set a limit, and hard caps on tokens, tool calls and wall time were added the same day. Every run now writes a trace that includes a salted hash of the user (links one person's runs without naming them), the tools called, tokens, latency, cost and the protocol flags, and never a name or a raw tool output1.

Nothing about the work system can be checked from outside, the account is a single author's, the employer is not named, and the rebuild, the incident and the caps are not dated more precisely than to the author's time on the system. It also reports no golden-set size, no correctness, silent-failure or refusal shares, and no comparison before and after the rebuild, so it supports no claim that the design improved the answers. A small public assistant built on related principles (numbers only from tool results, run-time caps and traces, though not the glossary or dashboard checks), with its last evaluation published, is sitewitness, which serves Ask the site8.
