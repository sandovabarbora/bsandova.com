An LLM assistant over a data warehouse: design notes

How an assistant that answers business questions from an employer's warehouse was rebuilt around the data catalogue, a cross-checking protocol and least-privilege tools, told from the author's records without internal figures.

Overwhelmed? Here's the short version
  • The assistant reads business definitions from the catalogue and, when a certified dashboard carries the same measure, reports how far its figure differs; otherwise it labels the answer unreconciled. How often such a dashboard exists is not published.
  • Its scores are not published, so this page describes a design, not how well it performs.
  • Write access was removed and every run has hard caps and a pseudonymous trace.
  • The work system rests on the author's records (private; not verifiable); the employer and its internal figures are not named.

What the assistant does and how it is built

Non-technical staff want answers to questions such as how many active customers did we have in Q2 in one market. Asked in their own words, the assistant returns a number, a chart and the query that produced it. It is judged on golden sets, fixed sets of real questions with verified answers, by the shares that come back correct, come back wrong without saying so (a silent failure) or are correctly declined; those shares are kept at work and not reported here1.

The version I inherited was a bespoke NL→SQL (natural language to SQL) service: retrieval of similar past queries, a custom prompt pipeline, and code that encoded what the business meant by its own words. Its replacement is a much smaller agent, a graph of steps on a commercial model API, connected to the warehouse, the data catalogue with its glossary and the certified dashboards through MCP (Model Context Protocol) connectors, adapters that expose each system to the model as callable tools. It had to match the old service on the golden sets before replacing it; the share of matching answers and the tolerance are in the private record1.

The main design choice keeps domain knowledge in the data catalogue, in the glossary terms, descriptions and lineage that analysts already maintain, which the agent reads at run time through lookup tools instead of a schema dump in the prompt. The codebase holds nothing about what a "customer" or a "tier" means, and a definition fixed in the catalogue reaches the agent on its next run without a code or prompt change. The agent looks the question's terms up, finds the certified figure if one exists or writes a query, runs it read-only, reconciles the result and answers with its provenance. Each step is a node of the graph with declared inputs and outputs, so a run's sequence of steps and tools can be reconstructed from its trace, though not replayed exactly, since the trace keeps no raw tool output. Text-to-SQL benchmarks such as Spider and BIRD score the SQL a model writes23; semantic layers such as the dbt Semantic Layer and LookML keep metric definitions in one governed place45, and this design is closest to them, with the existing catalogue as the semantic layer.

The trust protocol and the golden sets

Business terms resolve through the glossary before any SQL is written, so that "active customer" means what the company decided it means; that is a design aim, not a measured property. When a certified dashboard carries the same measure, the difference from it is reported; otherwise the answer says it is unreconciled. The harness scores whether each run followed the protocol as well as whether it was correct. What counts as agreement with a dashboard, and how often a certified figure exists, are not published here1.

The golden sets came from the first business proof of concept, run with business users in the room: their real questions became date-fixed golden cases with verified answers, and each definition they argued about was settled and written into the glossary the agent reads. The sets run on every change, so that a change that improves one score at the cost of another is meant to show before it ships; how often that has happened is not reported here1.

Quaesitor, an exploratory harness I ran on commercial models, not on the work system (not pre-registered; harness and run reports private), plants the usual causes of a wrong number in synthetic and real warehouses and asks each question with a known answer three times6. Of its 5 794 answers, 66 % were silently wrong; among the 3 704 numeric answers from five packs the share ranged from 56 % to 88 % across packs and from 76 % to 92 % across model configurations7, and on three smaller warehouses (10 to 80 cells per model) from 20 % to 80 % of all cells per model, declined cells included6. The traps are planted, so these rates say nothing about production. A separate study, Can a wrong number be seen coming?, asks whether a run-time signal can tell wrong answers from right ones and reports its own estimates and uncertainty7.

Tool surface, privileges, cost caps and tracing

Tools and privileges changed after a design discussion (private; not verifiable). The connectors exposed many more tools than a question-answering assistant needs, some able to write, so only a read-only allowlist (a fixed list) remains, and a scoping wrapper rejects any query reaching outside the user's project. The assistant also ran as a service account, a confused deputy through which a user could do what their own credentials could not, so access is now enforced per data domain by the warehouse's own permissions rather than by a prompt instruction1.

After a recorded incident in which a single unbounded question ran up a large token bill without failing, because nothing set a limit, hard caps on tokens, tool calls and wall time were added the same day. Every run now writes a trace with a salted hash of the user (linking one person's runs without naming them), the tools called, tokens, latency, cost and the protocol flags, never a name or a raw tool output1.

Nothing about the work system can be checked from outside, the account is a single author's, the employer is not named, and the rebuild, the incident and the caps are dated no more precisely than the author's time on the system. With no golden-set size, no shares and no before-and-after comparison reported, the page supports no claim that the design improved the answers. Sitewitness, which serves Ask the site, is a small public assistant on related principles (numbers only from tool results, run-time caps and traces, but no glossary or dashboard checks) with its last evaluation published8.
