AI engineering · Alma Career, Prague · 2025 → · the day job's LLM system, and what it taught

AI over data, measured.

The most common AI system in a company today is an assistant that answers business questions from a warehouse. It is also the easiest one to ship wrong, because a wrong number looks exactly like a right one. This is how I built one, measured it before anyone trusted it, hardened it after the measurements, and what I would tell an AI engineer who is about to build the next one. Employer data is left out, and the engineering is not. The public counterpart, on data anyone can inspect, is Quaesitor.

1 · What it is for, and what "working" means

Non-technical staff want answers to questions like how many active customers did we have in Q2 in Germany, and analysts are the bottleneck between them and the warehouse. The assistant lets them ask in their own words and get a number, a chart and the query that produced it. Whether it works is judged on a fixed set of real questions with verified answers rather than on how well it handles a demo question, and it is measured as three shares: the answers that come back correct, those that come back wrong without saying so, and those that correctly decline because the data cannot answer. These three numbers are how the product is measured, and every decision below was made to move them1.

2 · Architecture: an agent that reads the data catalogue

The first version I inherited was a ~4 500-line bespoke NL→SQL service: Vanna for retrieval over ChromaDB, a custom pipeline of prompts, and a growing body of Python that encoded what the business meant by its own words. It was replaced by a ~400-line LangGraph agent behind FastAPI on the Anthropic API, with MCP connectors to BigQuery (the warehouse), OpenMetadata (the catalogue and glossary) and Metabase (the certified dashboards). The main design choice was to keep domain knowledge in the data catalogue, as the glossary terms, descriptions and lineage that analysts already maintain, and to have the agent read it at run time, so nothing about what a "customer" or a "tier" means is in the codebase. The rebuild was chosen on maintenance cost per line, and it had to reach parity on the golden sets before it replaced anything1.

The graph is deliberately small: the agent reads the question, looks its terms up in the catalogue first, finds the certified figure if one exists and otherwise writes a query, runs it read-only, reconciles the result and answers with provenance. Every step is a node with a typed state, so a run can be replayed from its trace and a change to one node can be tested alone. Instead of a schema dump in the prompt, the agent gets tools to look things up. That keeps the context small, and when a definition is wrong, the catalogue is what gets fixed rather than the prompt1.

3 · The trust protocol

A number from an LLM is a claim, and the protocol turns it into either a checked claim or a refusal. Business terms resolve through the glossary before any SQL is written, so "active customer" means what the company decided it means. When a certified dashboard carries the same measure, the assistant's figure is reconciled against it and the difference is reported; when none exists, the answer says it is unreconciled. Whether a run followed the protocol is itself scored in the evaluation harness alongside correctness, so a right answer reached the wrong way counts against the system. Trust in an answer therefore rests on the protocol around the model rather than on the model, and a protocol can be measured1.

Quaesitor is built entirely on the same idea, in public. It plants the reasons a number goes wrong in a warehouse, asks questions with known answers three times each, and counts the results. There the silent-failure rate of frontier models ranges from 56 % to 92 % depending on the pack, and a follow-up study shows that nothing visible at run time predicts which answers are the wrong ones, which is why the cross-check is required2.

4 · Tool surface, privileges, cost caps and tracing

Each change in this section followed a measurement rather than a checklist. The connectors exposed 40 MCP tools, 18 of them write-capable, although an assistant that answers questions never needs to drop a table, so the surface was cut to a 15-tool read-only allowlist, and a project-scoping wrapper rejects any query that reaches outside the user's project before it gets to BigQuery. The assistant also ran as a service account, which made it a confused deputy, since a user could make the assistant's credentials do what the user's own could not. An instruction in the prompt can be talked around, so the fix was per-domain protection enforced at BigQuery IAM. Cost had no ceiling either, and a single unbounded question consumed 4.07 million input tokens and $21 without failing, because nothing said it should; hard caps on tokens, tool calls and wall time were added the same day. Cost is now a first-class field of every trace1.

Every run writes fourteen fields, among them a salted hash of the user, their team, the tools called, tokens in and out, latency, cost and the protocol-compliance flags, and it never writes a name or a raw tool output. The decision serves observability and privacy at once, and it is why the traces can be kept and analysed. They found a defect nobody had reported, a third-party MCP server whose malformed output schema silently and non-deterministically discarded results. Without per-run tool logs it would have been recorded only as the assistant being sometimes wrong1.

5 · Golden sets and the evaluation harness

The golden sets came from the stakeholders rather than from me. The first business POC ran with sales leads, a team manager and a category owner in the room, and their real questions became date-fixed golden cases with verified answers. Every ambiguous definition they argued about (category semantics, tier models, credit balances) was driven to an authoritative answer and written into the OpenMetadata glossary, so the agent inherits it instead of re-deriving it per question. The harness runs the golden sets on every change and reports correctness, silent failure, refusals and protocol compliance, so a change that improves one of them at the expense of another is visible before it ships, during development rather than in a phase at the end1.

6 · What I would tell the next AI engineer

Measure before you trust, and measure silent failure rather than accuracy, since a model that is confidently wrong 60 % of the time can have a demo that looks perfect. Put knowledge where people already maintain it, in the catalogue, and keep it out of the prompt and the code. Treat the agent as a user with least privilege, enforced at a layer it cannot be talked out of. Cap everything that can grow without bound, and log cost per run from day one. Trace every run pseudonymously so the traces can be kept. Get golden questions from the people who will ask them, fix their dates, and run them in CI. The Quaesitor measurements show that the wrong answers cannot be picked out from the outside, so build the cross-check instead of hoping2.

The live demonstration of these rules on this site is Ask the site: an agent over this site's own data files and texts, with every number coming from a tool call, every quotation verified verbatim, a cap per question, a budget per day, and the trace shown to the user. It is kept small on purpose, so that the rules stay in view. It has since become a package, sitewitness, which takes a folder of texts and JSON files and produces an agent with the five rules enforced in code, an evaluation runner and a trace page. This site is its first instance.
