AI engineering · Alma Career, Prague · 2025 → · the day job's LLM system, and what it taught

AI over data, measured.

The most common AI system in a company today is an assistant that answers business questions from a warehouse. It is also the easiest one to ship wrong, because a wrong number looks exactly like a right one. This is how I built one, measured it before anyone trusted it, hardened it after the measurements, and what I would tell an AI engineer who is about to build the next one. Employer data is left out; the engineering is not. The public counterpart, on data anyone can inspect, is Quaesitor.

1 · What it is for, and what "working" means

Non-technical staff want answers to questions like how many active customers did we have in Q2 in Germany, and analysts are the bottleneck between them and the warehouse. The assistant lets them ask in their own words and get a number, a chart and the query that produced it. "Working" is not "answers a demo question well". It is: on a fixed set of real questions with verified answers, the share that comes back correct, the share that comes back wrong without saying so, and the share that correctly declines because the data cannot answer. Those three numbers are the product, and every decision below was made to move them1.

2 · Architecture: knowledge in the catalogue, not in the code

The first version I inherited was a ~4 500-line bespoke NL→SQL service: Vanna for retrieval over ChromaDB, a custom pipeline of prompts, and a growing body of Python that encoded what the business meant by its own words. It was replaced by a ~400-line LangGraph agent behind FastAPI on the Anthropic API, with MCP connectors to BigQuery (the warehouse), OpenMetadata (the catalogue and glossary) and Metabase (the certified dashboards). The decisive design choice: domain knowledge lives in the data catalogue, as glossary terms, descriptions and lineage that analysts already maintain, and the agent reads it at run time. Nothing about what a "customer" or a "tier" means is in the codebase. The rebuild was chosen on maintenance cost per line, and it had to be at parity on the golden sets before it replaced anything1.

The graph is deliberately small: understand the question, look the terms up in the catalogue first, find the certified figure if one exists, otherwise write a query, run it read-only, reconcile, answer with provenance. Every step is a node with a typed state, so a run can be replayed from its trace and a change to one node is testable alone. The agent does not get a schema dump in the prompt; it gets tools to look things up, which keeps the context small and makes the catalogue, not the prompt, the thing to fix when it is wrong1.

3 · The trust protocol

A number from an LLM is a claim. The protocol turns it into a checked claim or a refusal. Catalogue first: business terms resolve through the glossary before any SQL is written, so "active customer" means what the company decided it means. Cross-check every figure: when a certified dashboard carries the same measure, the assistant's number is reconciled against it and the difference is reported; when none exists, the answer says it is unreconciled. Compliance is a metric: whether a run followed the protocol is scored in the evaluation harness alongside correctness, so a right answer reached the wrong way counts against the system. Trust is not a property of the model. It is a property of the protocol around it, and protocols can be measured1.

The same idea, in public, is the whole of Quaesitor: plant the reasons a number goes wrong in a warehouse, ask questions with known answers three times each, and count. There the silent-failure rate of frontier models ranges from 56 % to 92 % depending on the pack, and a follow-up study shows that nothing visible at run time predicts which answers are the wrong ones, which is why the cross-check is not optional2.

4 · Hardening, after measuring

Everything in this section was done because a measurement said so, not because a checklist did. Tool surface: the connectors exposed 40 MCP tools, 18 of them write-capable. An assistant that can drop a table does not need to, so the surface was cut to a 15-tool read-only allowlist, and a project-scoping wrapper rejects any query that reaches outside the user's project before it gets to BigQuery. Least privilege at the wall, not in the prompt: the assistant ran as a service account, which made it a confused deputy, a user could make the assistant's credentials do what the user's own could not. The fix was per-domain protection enforced at BigQuery IAM. A prompt is a suggestion; IAM is a wall. Cost caps: a single unbounded question consumed 4.07 million input tokens and $21 without failing, because nothing said it should. Hard caps on tokens, tool calls and wall time were added the same day, and cost is now a first-class field of every trace1.

Tracing without names: every run writes fourteen fields, including a salted hash of the user, their team, the tools called, tokens in and out, latency, cost and the protocol-compliance flags, and never a name, never a raw tool output. That is an observability decision and a privacy decision at once, and it is why the traces can be kept and analysed. The traces found a defect nobody had reported: a third-party MCP server returned a malformed output schema that silently discarded results, non-deterministically. Without per-run tool logs that would have been "the assistant is sometimes wrong"1.

5 · Evaluation as the development loop

The golden sets came from the stakeholders, not from me. The first business POC ran with sales leads, a team manager and a category owner in the room: their real questions became date-fixed golden cases with verified answers; every ambiguous definition they argued about, category semantics, tier models, credit balances, was driven to an authoritative answer and written into the OpenMetadata glossary, so the agent inherits it instead of re-deriving it per question. The harness runs the golden sets on every change and reports correctness, silent failure, refusals and protocol compliance; a change that improves one at the expense of another is visible before it ships. Evaluation is not a phase at the end. It is the loop1.

6 · What I would tell the next AI engineer

Measure before you trust, and measure silent failure, not accuracy; a model that is confidently wrong 60 % of the time can have a demo that looks perfect. Put knowledge where people already maintain it, in the catalogue, not in the prompt or the code. Treat the agent as a user with least privilege, enforced where it cannot be talked out of. Cap everything that can grow without bound, and log cost per run from day one. Trace every run pseudonymously so the traces can be kept. Get golden questions from the people who will ask them, fix the dates, and run them in CI. And when you cannot see which answers are wrong from the outside, which the data say you cannot, build the cross-check instead of hoping2.

The live demonstration of these rules on this site is Ask the site: an agent over this site's own data files and texts, with every number coming from a tool call, every quotation verified verbatim, a cap per question, a budget per day, and the trace shown to the user. It is small on purpose; the rules are the point. It became a package, sitewitness: a folder of texts and JSON files in, an agent with the five rules enforced in code, an evaluation runner and a trace page out; this site is its first instance.
