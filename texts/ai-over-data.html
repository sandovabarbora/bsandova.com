An LLM assistant over a data warehouse: design notes

How an assistant that answers business questions from a company warehouse was rebuilt around the data catalogue, a cross-checking protocol and least-privilege tools, told from the author's records without outcome figures.

What the assistant does and how it is built

Non-technical staff want answers to questions such as how many active customers did we have in Q2 in Germany. The assistant lets them ask in their own words and returns a number, a chart and the query that produced it. It is judged on a fixed set of real questions with verified answers, as the shares that come back correct, come back wrong without saying so (a silent failure), or are correctly declined; such sets are called golden sets, and those shares are kept at work and not reported here1.

The version I inherited was a bespoke NL→SQL (natural language to SQL) service of about 4 500 lines: Vanna for retrieving similar past queries from ChromaDB, a custom pipeline of prompts, and Python that encoded what the business meant by its own words2. It was replaced by a LangGraph agent (a graph of steps) of about 400 lines behind FastAPI on the Anthropic API, with MCP (Model Context Protocol) connectors, adapters that expose each system to the model as callable tools, to BigQuery (the warehouse), OpenMetadata (the catalogue and glossary) and Metabase (the certified dashboards). It had to match the old service on the golden sets before replacing it; the share of matching answers and the tolerance are part of the private record1.

The main design choice keeps domain knowledge in the data catalogue, as the glossary terms, descriptions and lineage that analysts already maintain, and has the agent read it at run time, so the codebase holds nothing about what a "customer" or a "tier" means. The agent looks the question's terms up in the catalogue, finds the certified figure if one exists or writes a query, runs it read-only, reconciles the result and answers with its provenance. Each step is a separate node of the graph with declared inputs and outputs, so the sequence of steps and tools in a run can be reconstructed from its trace, though not replayed exactly, since the trace keeps no raw tool output. Lookup tools replace a schema dump in the prompt, so a definition fixed in the catalogue reaches the agent on its next run without a code or prompt change. Text-to-SQL benchmarks such as Spider and BIRD score the SQL a model writes34, and semantic layers such as the dbt Semantic Layer and LookML keep metric definitions in one governed place56. This design is closest to the second, with the existing catalogue in the role of the semantic layer.

The trust protocol and the golden sets

Before a figure reaches the user, business terms resolve through the glossary before any SQL is written, so "active customer" means what the company decided it means. When a certified dashboard carries the same measure, the assistant's figure is compared with it and the difference is reported; when none exists, the answer says it is unreconciled. The harness scores whether each run followed the protocol as well as whether it was correct. What counts as agreement with a dashboard, and how often a certified figure exists at all, are not published here1.

The golden sets came from the first business proof of concept, which ran with sales leads, a team manager and a category owner in the room; their real questions became date-fixed golden cases with verified answers. Each definition they argued about, such as category semantics, tier models and credit balances, was settled and written into the OpenMetadata glossary, where the agent reads it. The golden sets run on every change, so a change that improves one score at the cost of another is visible before it ships1.

Quaesitor, an exploratory harness I ran on commercial models rather than on the work system (not pre-registered; harness and run reports private), plants the usual causes of a wrong number in synthetic and real warehouses and asks questions with known answers three times each7. Of its 5 794 answers, 66 % were silently wrong; among the 3 704 numeric answers from five packs the share ranged from 56 % to 88 % across packs and from 76 % to 92 % across model configurations8, and on three smaller warehouses (10 to 80 cells per model) from 20 % to 80 % of all cells per model, declined cells included7. The traps are planted, so these rates say nothing about production. No run-time signal separated wrong answers from right ones well: the best of eight models, chosen after the fact, reached a held-out AUC of 0.64 (95 % CI 0.51–0.77), where 0.5 is chance and 1 is perfect separation8.

Tool surface, privileges, cost caps and tracing

The tool surface and the privileges changed after a design review. The connectors exposed 40 MCP tools, 18 of them write-capable, which an assistant that answers questions never needs, so only a read-only allowlist (a fixed list) of 15 remains, and a scoping wrapper rejects any query that reaches outside the user's project. The assistant also ran as a service account, a confused deputy through which a user could do what the user's own credentials could not, so access is now enforced by per-domain protection in BigQuery IAM, the warehouse's own access permissions, rather than by a prompt instruction1.

The cost caps came from a recorded incident. A single unbounded question consumed 4.07 million input tokens and $21 without failing, because nothing set a limit, and hard caps on tokens, tool calls and wall time were added the same day. Every run now writes fourteen fields, among them a salted hash of the user (links one person's runs without naming them), the tools called, tokens, latency, cost and the protocol flags, and never a name or a raw tool output. The traces also exposed an unreported defect, a third-party MCP server whose malformed output schema dropped results at random1.

Nothing about the work system can be checked from outside, the account is a single author's, and the rebuild, the incident and the caps are dated only to the period from October 2025. It also reports no golden-set size, no correctness, silent-failure or refusal shares, and no comparison before and after the rebuild, so it supports no claim that the design improved the answers. A small public assistant built on related principles (numbers only from tool results, run-time caps and traces, though not the glossary or dashboard checks), with its last evaluation published, is sitewitness, which serves Ask the site9.
