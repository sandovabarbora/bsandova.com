Call-sheet conventions and the data model

A call sheet is issued the night before a shoot day and is often revised the same morning, with revisions named by colour or letter. FilmRunner stores each sheet as an ordered series of revisions, so that the changes since the version a crew member printed can be listed. Page counts are kept as an integer number of eighths of a page, the unit scripts are timed in, to avoid rounding in figures an assistant director adds up by hand, and cast status codes are a fixed set: W (working), SW (start work), WF (work finish), H (hold), SWF (start and finish) and R (rehearsal). The sheet also has to open offline, since call times fall early in the morning and many locations are outside mobile coverage. These conventions are taken from the project's design notes, which cite no industry source1.

The first build and why it was set aside

The author of this note is FilmRunner's founder, and every source cited below is her own private record. The first build, whose repository history runs from 17 January to 31 May 2026, was production management for mid-budget films: script import, an AI-drafted breakdown (the list of what each scene needs), a stripboard schedule (scenes ordered into shoot days) and the published call sheet, with company single sign-on, a data processing agreement, error reporting that strips personal data and Stripe, Twilio and Frame.io integrations around it. A commit message of 13 May 2026 records two critical fail-open defects, flaws that grant access when a check fails or a setting is missing, and four high-severity findings from a review of unknown origin, all fixed in that commit (private; not verifiable); the record does not say who or what made the review. A development-mode check compared the environment against "production", so a blank variable counted as development, and it was changed to an explicit list of development environments. Automatic account creation through single sign-on trusted the browser's claim about how the user had signed in, and it now checks the provider and a verified e-mail on the server2. On 14 September 2026 the author restarted around the call sheet alone, because the old repository had "accumulated surface area without a validated wedge"3.

The second build and what it lacks

The second build keeps only the call sheet. The back end is FastAPI, SQLAlchemy 2.0, Alembic and PostgreSQL, hosted on Fly.io in Frankfurt with Supabase used as plain Postgres; the front end is a React, Vite and TypeScript progressive web app, a web page that can be installed and run offline, which caches the last sheet in the browser. Sign-in uses Supabase Auth with a code or link sent by e-mail, and the API enforces each production's roles. Nine decision records cover the back-end and front-end stacks, hosting, the editor, sign-in, roles, location services, web push and rate limits on public endpoints3. The live demo serves a sample shoot day, and the editor is the assistant director's side of the same sheet. The repository's automated browser tests check that a sheet loaded once online still renders from the cache, marked as offline with the time it was saved, when its data request then fails6. That is a headless browser in a test, not a check on crews' phones, and no device test is recorded.

StudioBinder, SetHero, Movie Magic Scheduling, Yamdu and Croogloo already issue call sheets. The project's own desk research, built mostly from vendor pages and search snippets, could confirm offline viewing only for Movie Magic's exported PDF4; for the other four tools offline viewing is not confirmed either way. No pilot with an assistant director outside the project has run: the first is blocked on the author's own steps as of 28 September 2026, so there is no timed test or count of revisions handled on a real shoot day5.
