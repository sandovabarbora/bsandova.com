FilmRunner, an offline call sheet

A film-production platform cut down to its call-sheet module, a web app with ordered revisions that crews can open without signal; no pilot with a working crew has run yet.

Call-sheet conventions and the data model

A call sheet is issued the night before a shoot day and is often revised the same morning, with revisions named by colour or letter. FilmRunner stores each sheet as an ordered series of revisions, so that the changes since the version a crew member printed can be listed. Page counts are kept as an integer number of eighths of a page, the unit scripts are timed in, to avoid rounding in figures an assistant director adds up by hand, and cast status codes (W, SW, WF, H, SWF, R) are a fixed set. The sheet also has to open offline, since call times fall early in the morning and many locations are outside mobile coverage. These conventions are taken from the project's design notes, which cite no industry source1.

The first build and why it was set aside

The first build, whose repository history runs from 17 January to 31 May 2026, was production management for mid-budget films: script import, an AI-drafted breakdown, a stripboard schedule and the published call sheet, with SSO/SAML, a data processing agreement, Sentry with PII scrubbing and Stripe, Twilio and Frame.io integrations around it. A code review of one day's commits, recorded in the commit of 13 May 2026 that fixed its findings, reported two critical fail-open defects; the record does not name the reviewer. A development-mode check compared the environment against "production", so a blank variable counted as development, and it was changed to an explicit list of development environments. SSO auto-provisioning trusted the browser's claim that the user came from SAML, and it now checks the provider and a verified e-mail on the server2. On 14 September 2026 the founder restarted around the call sheet alone, because the old repository had "accumulated surface area without a validated wedge"3.

The second build and what it lacks

The second build keeps only the call sheet. The back end is FastAPI, SQLAlchemy 2.0, Alembic and PostgreSQL, hosted on Fly.io in Frankfurt with Supabase used as plain Postgres; the front end is a React, Vite and TypeScript PWA with an IndexedDB cache and a Workbox service worker. Sign-in uses Supabase Auth with a code or link sent by e-mail, and the API enforces each production's roles. Nine decision records cover the back-end and front-end stacks, hosting, the editor, sign-in, roles, location services, web push and rate limits on public endpoints3. The live demo serves a sample shoot day that still renders in airplane mode once added to a phone's home screen, and the editor is the assistant director's side of the same sheet.

StudioBinder, SetHero, Movie Magic Scheduling, Yamdu and Croogloo already issue call sheets. The project's own desk research, built mostly from vendor pages and search snippets, could confirm offline viewing only for Movie Magic's exported PDF4. No pilot with an assistant director outside the project has run: the first is blocked on the founder's own steps as of 28 September 2026, so there is no timed test or count of revisions handled on a real shoot day5.
