Overwhelmed? Here's the short version
  • At equal accuracy the model that declined more left fewer unflagged errors: on subscriptions, 54 silently wrong answers against 91.
  • On a standard schema, real taxi records and a two-system CRM and ERP warehouse, silent-failure rates ran from 20 % to 80 % per model, on 10 to 80 cells each, which is too few for more than a description.
  • Asked ten questions the data could not answer, one model declined two to five per language and the other at most one; both returned a number for a customer table that had stopped loading.
  • Schema documentation moved wrong answers closer to the verified value without making more of them correct; this rests on one model, one language and 26 questions.

The question

A silent failure is an answer that runs without error, looks plausible and is wrong, with nothing downstream to say it should not be trusted. Text-to-SQL benchmarks such as Spider and BIRD score execution accuracy12, which folds two outcomes, declining and returning a wrong number, into one "not correct". The literature on abstention treats declining as a separate behaviour with its own costs3. For someone reading the numbers the two outcomes differ, because a refusal prompts a follow-up question and a wrong number does not4. The question here is how two assistants split their non-correct answers between the two.

The warehouses were built with the traps in known places (a null inside an aggregate here, a batch loaded twice there; the full list is the second text), each question has a verified query written by hand, and each answer was classified by rule as correct, silently wrong, implausible, declined, invalid or without a figure5. The questions were asked in fifteen languages, three repeats each, of two models called under the aliases opus and sonnet; the tables below give one verdict per question and language, as in the original pages, which carry the run fingerprints46. Across all packs and configurations the 125 run reports hold 5 794 answers, one per question and repeat, of which 9 are unmeasured because the model call failed7.

What the table does show is where the non-correct answers went: at the same correct count on subscriptions, the model that declined more left 54 silently wrong answers against 91 for the other, so choosing between them changes the mix of refusals and unflagged errors more than the number of right answers.

On the real taxi records sonnet was silently wrong in 80 % of 80 cells and opus in 70 %, against 70 % and 58 % on the planted retail pack. Opus, which declined 55 times on retail, declined 8 times out of 80 on taxi. Outside the two planted packs each model has between 10 and 80 cells, so these rates describe the runs and support no comparison between warehouses.

Ten questions past the edge of the data

The abstention pack has ten questions that reach past the edge of what the warehouse holds. Every column they need exists, so every query runs and returns a number, and the number counts the rows that match rather than answering the question11. One example asks how many customers registered in July 2026. Orders run through August 2026, so the period looks covered. One model wrote this:

SELECT COUNT(*) AS new_customers
FROM dim_customer
WHERE registered_date >= DATE '2026-07-01'
  AND registered_date <  DATE '2026-08-01'
  AND is_test_account = FALSE

The query excludes test accounts and returns zero. The customer dimension stopped being written to in February 2025, eighteen months earlier, so the zero reflects a table that is no longer filled, and nothing in the result distinguishes that from a month without sign-ups. Both models answered both questions in that category with a number11.

Declining is the correct answer to all ten. In Czech, opus declined five of ten and sonnet none; across fifteen languages opus declined two to five per language and sonnet zero or one11. An earlier version of the pack asked for quantities with no column behind them (a gross margin where nothing records cost), and both models declined all ten; the current version keeps every column and removes only the data, and only this version separated the two models.

Correctness and error size with schema documentation

A common remedy is to give the model documentation of the schema and the metrics. The retail pack was run with and without it, 26 questions, three repeats, Czech, with only that input changed; the SHA-256 digests of both runs' inputs are recorded on the original page6.

Correct answers were 2 of 26 without documentation and 2 of 26 with it (exact McNemar, p = 1.00). The size of the error changed: across the 22 questions measurable in both runs the median absolute error fell from 72 % to 23 %, with 15 answers closer to the verified value and 2 further (exact sign test, p = 0.0023). The comparison was run three times, and the sign-test p-values of the three runs were 0.00008, 0.00073 and 0.0023; the figures above are those of the third run, in a clean environment6.

Answers that had been implausibly far from the verified value came back within a plausible range, and none moved the other way; a revenue figure off by about six hundred per cent came back off by about seventy. The prediction before the run was that documentation would reduce refusals, and it did not.

What this does not show

The documentation result rests on 26 questions, one warehouse, one model, one language and two conditions. It is not evidence about documentation in general, and it does not show that documentation raised the silent-failure rate (77 % → 85 %, p = 0.73, within noise at this size)6. The rates in both tables are counts of cells without intervals, the warehouses outside the two planted packs carry 10 to 80 cells per model, and the harness recorded neither a sampling temperature nor a seed. The run reports, the verified queries and the comparison tables are in a private repository, so a reader can check the tables against the original pages but cannot rebuild them, and one row of table 1 no longer matches the files now in the repository. The traps are planted in synthetic warehouses, so the rates say nothing about how often these failures occur in production.
