Silent failure as accuracy rises: method and prior evidence

The argument behind Quaesitor, that wrong answers get harder to catch as assistants grow more accurate, is untested here; this text sets out the method used and eight findings by others, including the strongest objection.

Overwhelmed? Here's the short version
  • A verified question needs a written metric definition, a hand-written query reconciled against a trusted figure, three repeats per language and a rule-based classification of each answer; the queries, not the model calls, were the costly part.
  • Published work by others finds that benchmark accuracy falls sharply on private warehouses, that most wrong queries are schema errors that still return a plausible number, and that agreement across samples does not indicate correctness.
  • The strongest objection, that a semantic layer fixes the problem, is backed by a paired benchmark; it reports accuracy only, so it cannot say whether the remaining errors became harder to notice.
  • Nothing here tests whether users check less as accuracy rises; the text is an argument supported by other people's results and by the runs in texts 1 and 2.

The argument

Ask a data assistant how many customers made a second purchase within thirty days of their first. The verified query counts thirty days from the first purchase and returns 621. A model that anchors the window to the registration date returns 684, which the original page reports for ninety-five attempts across the runs1. Both queries are valid SQL and both run. The second answer is 10.1 % too high, a size that looks ordinary, whereas an answer off by eighty-five per cent would be queried.

Quaesitor was a one-person service that measured such silent failures: it put an assistant in front of a warehouse, asked questions with a hand-verified answer and counted how often the answer was wrong without any warning. The argument behind it was that a model right nine times in ten may be more dangerous than one right four times in ten, because at four in ten a reader checks everything and at nine the checking stops. None of the runs tests that claim; it would need data on how people check answers, which the service did not collect. The service is closed, and this text records the method and the evidence it relied on.

Adjacent tools

Three kinds of tool sit next to this problem. Semantic layers define what a metric means, but do not verify that the definition matches the data or that the model used it. Evaluation and observability platforms measure consistency, latency, cost and text-level hallucination, and cannot decide whether a number is right without the metric's definition, the grain and the data model. Governance platforms record who asked what and whether data left the organisation, which shows that the assistant stayed within the rules rather than that the answer was true2.

The model calls were the cheap part: a run cost a few dollars, and the taxi run in English recorded 1.78 USD. The costly part was the verified query behind every question, written by hand against the schema, reconciled against a number the owner already trusted and read clause by clause with the person who owns the definition. On an organisation's own warehouse nobody knows the right answer in advance, which is why that work has to be done before anything can be scored.

How a question became a verified one

The method has five steps3. The owner of a metric states its definition in writing. A query is written to implement it and read against the definition clause by clause. The query is reconciled against a figure the business already trusts, such as a certified report or a finance close. The question is then asked of the assistant three times in each language the business uses, and every answer is classified by rule as correct, silently wrong, implausible or declined, with the rule that fired printed beside it, so that the verdict does not depend on a model's judgement. Finally the questions, both queries, the warehouse builders and the runs with their fingerprints are handed over. A verified query can itself be wrong; one was found wrong and the correction was stated in a client's report (private; not verifiable)4.

The original site injected every figure from the runs at build time and refused to build when a sentence was no longer supported by them. That rule did not catch one mislabelled figure: the builder summed the "model calls" row of the 125 run reports, 5 790, and printed it as "measured answers". The reports hold 5 794 answers, one per question and repeat, of which 9 were not measured because the model call failed; this site now uses 5 7945.

Prior evidence

Eight results the argument depends on were established by other authors. On BEAVER, a benchmark of 9 128 question–query pairs from real private warehouses, a state-of-the-art agentic framework using GPT-5.2 reached 10.8 % accuracy, and 30.1 % with oracle hints6; its authors contrast this with the much higher scores reported on public benchmarks7. An analysis of 4 602 incorrect queries, as reported by Davidson, attributes 81.2 % of them to schema-level errors such as the wrong column or a misread term8, and a worked example on a 35-table schema shows a join that duplicates rows and returns 271 049 where 154 050 is correct, without any error being raised9. A taxonomy validated against fifty incidents from court documents and regulatory filings finds that 53 % of verifiable public failures were silent10.

Declining carries a measurable trade-off. In dataset retrieval on the open web, a baseline agent answered 40 % more questions while an agent using semantic metadata achieved 65.7 % higher precision11, and the choice between trusting the model, trusting the context and abstaining is scored on about 69 000 query–context instances per model elsewhere12. In the abstention pack of text 1 the two models differed more on this axis than on any other measured. Agreement is a weak signal: under dense retrieval, 59 % of errors showed no dispersion across five samples13. In the Quaesitor runs, keeping only answers on which all three attempts agreed left the error rate at 84.9 % against 85.1 % and cost about twenty points of coverage, as published1; the detector study reaches a similar conclusion on the same runs.

The language of the question can matter: an accuracy gap of 8.79 % is reported for Arabic against English on Spider14, which is why the runs used fifteen languages. Korolev argues that the cost of silent failures falls on the decisions made from them rather than on the pipeline that produced them15.

The strongest objection is that a semantic layer fixes the problem. In a paired benchmark of 100 questions, giving the model a semantic layer raised accuracy from 50.5 % to 67.7 % for Claude Opus 4.7, from 46.5 % to 68.7 % for Claude Sonnet 4.6 and from 45.5 % to 68.7 % for GPT-5.416. The benchmark reports accuracy without classifying the remaining errors, so it cannot show whether they became easier or harder to notice. The documentation run in text 1, one model on 26 questions, found correctness unchanged and the remaining errors smaller, which is consistent with the argument but far too small to settle it.

What remains

The name is the Latin title of the Roman magistrate who presided over a court of inquiry. The service is closed. The runs, 5 794 answers in fifteen languages over five warehouses, remain in a private repository, and their results are published on the original pages with run fingerprints4. The harness that produced them is in the same private repository17. quaesitor-zero is public: a small check that generates questions a schema cannot answer and scores whether an assistant declines them, released under Apache-2.0 on PyPI and described in its README as having no network code, telemetry or model access18. The service's findings were dated statements with the queries attached; they were not an accredited certification, a conformity assessment or a statutory audit.

What this does not show

This text argues rather than measures. The claim that checking falls as accuracy rises is not tested by any Quaesitor run, and the external results come from different tasks, models and schemas. The cohort example and the agreement figures are quoted as first published, from runs in a private repository. Two of the cited pages refuse automated access and were not re-read for this version.
