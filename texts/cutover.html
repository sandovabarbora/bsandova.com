How to prove a cutover

A migration is finished when nothing changed. Not "the tests pass", not "the numbers look right": zero mismatches across every column and an identical fingerprint for every day, computed before a single consumer is repointed. I used the method on a five-year salary pipeline and a 62-day event backfill1. This is it as a tool anyone can run, and what it found on its first real dataset.

Why the number that matters is zero

Two cutovers from the day job. A salary-recompute pipeline moved from a standalone extractor to an incremental dbt-python model; before any downstream consumer was repointed, the new model was compared with the old one across five years of history and twenty columns, and the result was zero mismatches. A production GA4 event-stream backfill was validated by a full-row fingerprint per day: 62 of 62 days identical to the pre-backfill snapshot, development identical to production1. Neither argument was "we tested it". Both were a number, and the number was zero.

The method behind both is small enough to be a package. Two tables, a key, optionally a partition column, and a fixed sequence of questions asked in an order where each one only makes sense if the previous one passed. cutover is that sequence, in DuckDB over Arrow tables, with a text, JSON and self-contained HTML report and exit codes that a CI job can gate on2.

pip install cutover
cutover old.parquet new.parquet --key id --partition day --tol amount=0.01 --html report.html

Six steps, in order

1 · Schema. Columns only on one side, and shared columns whose type changed. The comparison continues on the shared columns with equal types; the rest is reported, and by default any of it fails the run. A type change is not a formatting detail. It is usually the first symptom of a different pipeline making different assumptions, which the demo below illustrates.

2 · Key. NULL keys and duplicate keys on each side. A non-unique key on either side fails with key_not_unique and the column step is skipped, because a per-column diff on a non-unique key would silently compare arbitrary pairs of rows and report nonsense with confidence.

3 · Row set. Keys only in the old table, keys only in the new, keys in both. Counts and samples. Most cutover failures are here: a filter that changed, a source that was late, a join that dropped the rows with no match.

4 · Columns. On keys present on both sides, per column, the number of rows where the values differ, with NULL = NULL. Exact equality for everything except floats and decimals with a declared tolerance, where two values are the same when

$$|a - b| \le \tau_{\text{abs}} + \tau_{\text{rel}}\,|b|$$

Every tolerance is declared per column and printed in the report, so a reader can see what was allowed to differ. A tolerance you did not declare does not exist; the tool does not decide on its own that 12.059999999999999 is 12.06.

5 · Fingerprints. For each value of the partition column, a hash of all rows in that partition ordered by key, on each side. The report says identical / total partitions and lists the ones that differ, which is how "62 of 62 days" is computed. The hash is exact, so columns with a declared tolerance are excluded from it and the report says which. If the partition column itself changed type, the fingerprints are not computed at all and the reason is partition_type_differs; comparing the hash of 2025-01-01 with the hash of 2025-01-01 00:00:00 would report 66 partitions for 33 days, which is what the first version of the tool did on the demo before the demo corrected it.

6 · Verdict. PASS only when the schema is clean, the key is unique, both row-set differences are zero, every column has zero mismatches within its declared tolerance and every partition fingerprint matches. Anything else is FAIL, with a list of reasons a script can read.

The sequence matters. Comparing columns before checking the key gives confident nonsense. Comparing fingerprints before comparing columns tells you that a day differs without telling you why. Comparing values before comparing schema hides that a DATE became a TIMESTAMP.

The demo, and what it found

A month of NYC yellow-taxi trips, January 2025, about 3.3 million rows in one public parquet file3. Two independently written aggregations of it into (day, pickup zone) → trips, fare, kilometres: a "legacy" one in pandas, dropping non-positive fares, summing floats, converting miles to kilometres at the end; and a "new" one in SQL in DuckDB with the same intent, rounding the fare sum to cents. Then cutover on the two results with key (day, zone), partition by day, and a 10−6 tolerance on kilometres for the multiplication order2.

--- run 1
cutover: FAIL
rows: old 7,280 · new 7,280 · matched on key 7,280 · only in old 0 · only in new 0
columns: 1 / 3 columns with mismatches
  fare: 343 mismatches
fingerprints: 0 / 0 partitions identical by day
schema: type changes [('day', 'date32[day]', 'timestamp[us]')]
reasons: schema_drift, column_mismatch:fare, partition_type_differs

Three findings, none of them planted. The type change: DuckDB returned day as a DATE, and the DuckDB-to-pandas bridge turned it into a datetime; the pandas side had a calendar date. Both sides agreed on the key, so a row-count check would have passed. The schema step caught it, and it is the reason the fingerprints refused to run. The 343 fare mismatches: every one of them is floating-point noise, the largest absolute difference is 3.6 × 10−12, the pandas sum of 12.06 arriving as 12.059999999999999 against SQL's rounded 12.06. The tool is right not to forgive it on its own; the fix is a declared half-cent tolerance, visible in the report. The row set: 7 280 groups on both sides, 0 and 0, on 33 days, because the "January" file contains trips dated 31 December and 1 February. That is the source, not the pipelines, and both pipelines agreed on it.

--- run 2 · day cast to date on the new side, --tol fare=0.005
cutover: PASS
rows: old 7,280 · new 7,280 · matched on key 7,280 · only in old 0 · only in new 0
columns: 0 / 3 columns with mismatches
fingerprints: 33 / 33 partitions identical by day

Both reports are published as the tool wrote them: run 1, run 2, with the JSON next to each. The script that produced them is tools/cutover_demo.py in the site repository; it downloads the file, builds both aggregates, runs both comparisons and writes the reports, so the numbers above are not typed2.

What it does not do

It does not push the comparison into a remote warehouse; both tables are read into Arrow and compared locally in DuckDB, which spills to disk and is fine for tens of millions of rows and not the right tool for billions. It has no rules for acceptable schema evolution; a rename is a drop and an add. It does not know which side is right. A cutover proof shows that the new thing equals the old thing, and if the old thing was wrong, so is the new one, with a certificate. The judgement about which side to trust stays with the person running it, which is where it belongs.
