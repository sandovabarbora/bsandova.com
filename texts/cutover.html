cutover: checking that a table migration changed nothing

A Python package that compares two versions of a table in six ordered checks; on a month of NYC taxi aggregates it failed a first run on two differences and passed once both were addressed.

Overwhelmed? Here's the short version
  • The tool reads two tables, a key and an optional partition column, and reports FAIL with machine-readable reasons unless schema, key, rows, values and per-partition hashes all agree. Float columns may carry a declared absolute or relative tolerance, printed in the report.
  • The two differences in the demo were a day column that the conversion to pandas had turned into a timestamp, and fare sums that one side rounded to cents and the other did not; the half-cent tolerance declared for the fare is printed in the report.
  • Its evidence is its own test suite and that one public demo. The two cutovers at work that the method comes from were done by hand before the package existed.
  • It shows that two tables are equal, not that either is right, and it has not been measured on inputs larger than the demo.

What it does, and comparable tools

cutover shows whether a rewritten pipeline's output equals the old one before its consumers are repointed, given two tables, a key and optionally a partition column such as a date. It runs in DuckDB over Arrow tables, writes text, JSON and HTML reports, and exits with 0 for PASS, 1 for FAIL and 2 for an error, so that a CI job can gate on it1. The method comes from two cutovers in the author's day job: a salary pipeline compared over five years and twenty columns with zero mismatches, and an event-stream backfill with 62 of 62 days identical by full-row fingerprint. Both were done with ad-hoc queries before this package existed, and the records are private and cannot be checked2.

Several tools already do parts of this. datacompy compares two DataFrames on join columns, with absolute and relative tolerances, on pandas, Polars, Spark and Snowflake, and reports per-column mismatch counts3. Datafold's open-source data-diff compared tables within or across databases by checksumming key ranges and splitting the ranges that differ; Datafold stopped developing it on 17 May 20244. dbt-audit-helper provides macros that classify rows as added, removed, identical or modified, compare column values and, on some warehouses, hash whole queries5, and SQLMesh's table_diff reports a schema diff and a row diff between two tables6. cutover differs in three narrow ways. It makes the checks conditional on one another, so values are not compared on a non-unique key and partitions are not hashed when the partition column changed type. It hashes every partition, so the result can be stated as identical / total days. It does not push work into a warehouse, as data-diff and the dbt and SQLMesh tools do.

Method: six checks in a fixed order

The first check lists columns present on only one side and shared columns whose type changed; comparison continues on the shared columns with equal types, and by default any schema difference fails the run. The second check looks for NULL and duplicate keys on each side. A non-unique key fails with key_not_unique and the column step is skipped, because a per-column diff on such a key would compare arbitrary pairs of rows. The third compares the row sets, with counts and samples of keys found only in the old table, only in the new one, and in both.

The fourth check compares values on the keys present on both sides, counting per column the rows where the values differ, with two NULLs counted as equal. Equality is exact unless a tolerance is declared for a float or decimal column. A tolerance is either absolute or relative, one per column, and two values \(a\) (old) and \(b\) (new) count as equal when

$$\begin{aligned} |a - b| &\le \tau &&\text{(absolute), or}\\ |a - b| &\le \tau\,|b| &&\text{(relative)} \end{aligned}$$

On the command line, --tol fare=0.005 sets an absolute tolerance and --tol fare=rel:1e-6 a relative one. Every tolerance is printed in the report, and none is applied unless it was declared.

The fifth check computes fingerprints. For each value of the partition column, on each side, it takes the key columns and every value column without a tolerance, casts each to text in DuckDB, joins them with the unit separator U+001F (with U+0000 standing for NULL), joins the rows in key order with newlines, and takes the MD5 of the result. Columns with a tolerance are left out of the hash and named in the report. If the partition column changed type, no fingerprints are computed and the reason given is partition_type_differs. The sixth step is the verdict: PASS only when the schema is clean, the key is unique, neither side has keys the other lacks, every column has zero mismatches within its tolerance, and every partition fingerprint matches.

Edge cases were checked against version 0.1.0. A NaN equals a NaN in an exact column, but a NaN in a column with a tolerance is a mismatch, because the difference is not a number. The values −0.0 and 0.0 are equal in the column step but have different text forms, so they change the fingerprint. Two timestamp columns in different time zones are a type change and fail the schema step, even when they hold the same instants; with --allow-schema-drift such a column is listed under type changes and left out of the comparison, so its values are not checked at all.

Worked example: a month of NYC taxi trips

The demo reads the January 2025 yellow-taxi file from the NYC Taxi & Limousine Commission, about 3.3 million trips in one parquet file7, and turns it into (day, pickup zone) → trips, fare and kilometres twice. The legacy version is written in pandas, drops non-positive fares, sums fares as floats without rounding and converts miles to kilometres at the end. The new version is written in SQL in DuckDB with the same intent and rounds the fare sum to cents. The comparison uses the key (day, zone), is partitioned by day, and declares an absolute tolerance of 10−6 on kilometres for the different order of multiplication8.

--- run 1
cutover: FAIL
rows: old 7,280 · new 7,280 · matched on key 7,280 · only in old 0 · only in new 0
columns: 1 / 3 columns with mismatches
  fare: 343 mismatches
fingerprints: 0 / 0 partitions identical by day
schema: type changes [('day', 'date32[day]', 'timestamp[us]')]
reasons: schema_drift, column_mismatch:fare, partition_type_differs

The first run gave two findings and one observation, none of them planted. The first is the type change: DuckDB returned day as a DATE, the conversion to pandas turned it into a timestamp, and the pandas side had a calendar date. A row-count check would have passed, and the type change is why no fingerprints were computed. The second finding is 343 fare mismatches, all of them floating-point differences between an unrounded float sum and a sum rounded to cents; the pandas sum for zone 9 on 1 January is 12.059999999999999 against SQL's 12.06. Across all 343 rows the largest absolute difference is 3.6 × 10−12. The observation concerns the row set, which matched with 7 280 groups on each side, spread over 33 days because the January file contains trips dated 31 December and 1 February, a property of the source.

--- run 2 · day cast to date on the new side, --tol fare=0.005
cutover: PASS
rows: old 7,280 · new 7,280 · matched on key 7,280 · only in old 0 · only in new 0
columns: 0 / 3 columns with mismatches
fingerprints: 33 / 33 partitions identical by day

The half-cent tolerance in the second run states the intended contract: the new side rounds to cents and the legacy side does not, so any difference below half a cent is rounding and any larger one is a real change. Re-running the second comparison on 29 September 2026 with an absolute fare tolerance of 10−9 gave PASS, and with 10−12 it gave FAIL on fare. Both reports are published as written, run 1 and run 2, with JSON next to each8.

Tests and measured error

The package has 41 tests, run on Python 3.10 to 3.13 in GitHub Actions and passing locally on 29 September 2026. They plant faults in small tables, such as a dropped row, a duplicated key, a changed value, a changed type and a value turned into NULL, and require each one to be found and named in the reasons; others cover the sources, the report formats and the command line1. No error rate has been measured on real migrations; the evidence is these tests and the taxi demo.

Limits

Both tables are read into Arrow and compared locally in DuckDB, which can spill to disk and accepts a memory limit through --memory. The largest comparison run so far is the demo's, 7 280 aggregated rows built from about 3.3 million trips, and no benchmark on larger inputs has been made, so the size at which the tool stops being practical is unknown. A renamed column counts as one dropped and one added. It also cannot tell which side is right: if the old table was wrong, a PASS shows only that the new one is wrong in the same way, and that judgement stays with the person running it.

Install and reproduce

The package installs with pip install cutover and needs only DuckDB and pyarrow; a typical call is cutover old.parquet new.parquet --key id --partition day --tol amount=0.01 --html report.html. To reproduce the demo, clone the site repository and run uv run --with cutover --with pandas python tools/cutover_demo.py. The script downloads the 59 MB parquet file on its first run, builds both aggregates, runs both comparisons and writes the reports to assets/cutover/, in a few seconds on a laptop after the download8.
