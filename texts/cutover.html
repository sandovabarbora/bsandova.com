How to prove a cutover

A migration is finished when it can be shown that nothing changed, meaning zero mismatches across every column and an identical fingerprint for every day, computed before a single consumer is repointed. I used the method on a five-year salary pipeline and a 62-day event backfill1. This page presents it as a tool anyone can run, together with what it found on its first real dataset.

Two cutovers at work, and the method behind them

The method comes from two cutovers in the day job. A salary-recompute pipeline moved from a standalone extractor to an incremental dbt-python model, and before any downstream consumer was repointed, the new model was compared with the old one across five years of history and twenty columns, with zero mismatches. A production GA4 event-stream backfill was validated by a full-row fingerprint per day, with 62 of 62 days identical to the pre-backfill snapshot and development identical to production1. In neither case did the argument for the cutover rest on having tested it; in both it rested on a count of differences, and the count was zero.

The method is small enough to be a package. It takes two tables, a key and optionally a partition column, and asks a fixed sequence of questions in an order where each one makes sense only if the previous one passed. cutover is that sequence, run in DuckDB over Arrow tables, with a text, JSON and self-contained HTML report and exit codes that a CI job can gate on2.

pip install cutover
cutover old.parquet new.parquet --key id --partition day --tol amount=0.01 --html report.html

The six checks: schema, key, row set, columns, fingerprints, verdict

The first check is the schema. It lists columns present on only one side and shared columns whose type changed. The comparison continues on the shared columns with equal types, the rest is reported, and by default any of it fails the run. A type change is usually the first symptom of a different pipeline making different assumptions rather than a formatting detail, as the demo below illustrates.

The second check looks for NULL keys and duplicate keys on each side. A non-unique key on either side fails with key_not_unique and the column step is skipped, because a per-column diff on a non-unique key would silently compare arbitrary pairs of rows and report nonsense with confidence.

The third check compares the row sets, giving counts and samples of keys only in the old table, keys only in the new one and keys in both. Most cutover failures show up here, as a filter that changed, a source that was late or a join that dropped the rows with no match.

The fourth check compares columns on the keys present on both sides, counting per column the rows where the values differ, with NULL = NULL. Equality is exact for everything except floats and decimals with a declared tolerance, where two values are the same when

$$|a - b| \le \tau_{\text{abs}} + \tau_{\text{rel}}\,|b|$$

Every tolerance is declared per column and printed in the report, so a reader can see what was allowed to differ. The tool applies no tolerance that was not declared, and it does not decide on its own that 12.059999999999999 is 12.06.

The fifth check computes fingerprints. For each value of the partition column, it hashes all rows in that partition ordered by key, on each side. The report gives identical / total partitions and lists the ones that differ, which is how "62 of 62 days" is computed. The hash is exact, so columns with a declared tolerance are excluded from it and the report says which. If the partition column itself changed type, the fingerprints are not computed at all and the reason given is partition_type_differs. Comparing the hash of 2025-01-01 with the hash of 2025-01-01 00:00:00 would report 66 partitions for 33 days, which is what the first version of the tool did on the demo before the demo corrected it.

The sixth step is the verdict. It is PASS only when the schema is clean, the key is unique, both row-set differences are zero, every column has zero mismatches within its declared tolerance and every partition fingerprint matches. Anything else is FAIL, with a list of reasons a script can read.

The order of the checks matters because each one relies on the checks before it. Comparing columns before checking the key gives confident nonsense, comparing fingerprints before comparing columns shows that a day differs without showing why, and comparing values before comparing schema hides that a DATE became a TIMESTAMP.

The demo on a month of NYC taxi trips

The demo uses a month of NYC yellow-taxi trips, January 2025, about 3.3 million rows in one public parquet file3. Two independently written aggregations turn it into (day, pickup zone) → trips, fare, kilometres. The "legacy" one is written in pandas; it drops non-positive fares, sums floats and converts miles to kilometres at the end. The "new" one, in SQL in DuckDB, has the same intent and rounds the fare sum to cents. cutover then compares the two results with key (day, zone), partitioned by day, with a 10−6 tolerance on kilometres to allow for the multiplication order2.

--- run 1
cutover: FAIL
rows: old 7,280 · new 7,280 · matched on key 7,280 · only in old 0 · only in new 0
columns: 1 / 3 columns with mismatches
  fare: 343 mismatches
fingerprints: 0 / 0 partitions identical by day
schema: type changes [('day', 'date32[day]', 'timestamp[us]')]
reasons: schema_drift, column_mismatch:fare, partition_type_differs

The first run produced three findings, none of them planted. The first is the type change. DuckDB returned day as a DATE and the DuckDB-to-pandas bridge turned it into a datetime, while the pandas side had a calendar date. Both sides agreed on the key, so a row-count check would have passed; the schema step caught the change, and it is the reason the fingerprints were not computed. The second is the 343 fare mismatches, every one of which is floating-point noise. The largest absolute difference is 3.6 × 10−12, with the pandas sum of 12.06 arriving as 12.059999999999999 against SQL's rounded 12.06. The tool is right not to forgive this on its own, and the fix is a declared half-cent tolerance that is visible in the report. The third concerns the row set, which matched with 7 280 groups on both sides and 0 keys missing in either direction, spread over 33 days because the "January" file contains trips dated 31 December and 1 February. That is a property of the source rather than of the pipelines, and both pipelines agreed on it.

--- run 2 · day cast to date on the new side, --tol fare=0.005
cutover: PASS
rows: old 7,280 · new 7,280 · matched on key 7,280 · only in old 0 · only in new 0
columns: 0 / 3 columns with mismatches
fingerprints: 33 / 33 partitions identical by day

Both reports are published as the tool wrote them: run 1, run 2, with the JSON next to each. The script that produced them is tools/cutover_demo.py in the site repository; it downloads the file, builds both aggregates, runs both comparisons and writes the reports, so the numbers above were produced by the run and none of them was typed by me2.

Limits of the tool

cutover does not push the comparison into a remote warehouse. Both tables are read into Arrow and compared locally in DuckDB, which spills to disk and is fine for tens of millions of rows but is not the right tool for billions. It has no rules for acceptable schema evolution, so a rename counts as a drop and an add. Nor does it know which side is right: a cutover proof shows that the new thing equals the old thing, so if the old thing was wrong, the new one is wrong too, now with a certificate, and the judgement about which side to trust stays with the person running it.
